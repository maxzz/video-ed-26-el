The console shows a V8 out-of-memory crash during playback seeks. I’ll trace the skip-forward and skip-backward path and the terminal output to find what is leaking.

The renderer is running out of memory after a handful of seeks. I’ll look at the skip and playback path for objects that pile up each time.

The crash is a renderer out-of-memory error after a few seeks. The meeting file is 287 MB, so I’ll check whether each seek is keeping another copy of the media in JavaScript.

The protocol and video element stay flat under seeks, so the leak is in the playback UI path. I'll trace that next.

The renderer is already dead from the out-of-memory crash. I'll restart it with a debug port and measure the heap while seeking.

The eval worker imports the module that creates it, so each worker starts another. Vite keeps that import, and the renderer fills with workers until it runs out of memory.

The renderer was running out of memory because the expression-eval worker was spawning copies of itself until the JavaScript heap died. Skipping along the timeline was when that showed up, because the workers had already been multiplying since the editor loaded.

`eval-worker.ts` imported its message types from `eval.ts`. That file is the one that constructs the worker. Vite keeps a runtime import even for a type-only import, so each worker loaded `eval.ts`, which started another worker. A fresh launch produced more than a thousand workers in a few seconds, then the same V8 out-of-memory crash as in your console.

The message types now live in `eval-protocol.ts`, which does not create a worker. After that change, loading the Rocket Man MP3 and the meeting MP4, playing, and seeking eight times each left a single worker and a steady heap of about 40–50 MB.

**User**

Can you compare why this issue was not a problem in the original project "https://github.com/mifi/lossless-cut", but starts appear in out project and was it the best fix comparing to the original project solution?

---

**Cursor**

The original project handles this worker differently. I'll compare that setup with ours and with the change we made.

LosslessCut never loads the worker-creating module from inside the worker. This project did, because of one import and Vite 8.

In LosslessCut the worker file starts with a type-only import:

```ts
import type { RequestMessageData, ResponseMessageData } from './eval';
```

`eval.ts` is the module that calls `new Worker()`. The `import type` statement is deleted entirely when the worker is bundled, so the worker never runs that module. LosslessCut also builds with Vite 7.3.5. One worker is created, and it stays one worker.

The port wrote the same import with an inline type modifier:

```ts
import { type RequestMessageData, type ResponseMessageData } from "./eval";
```

Vite 8.3.2, which this project uses, does not drop that form. The worker bundle we fetched from the dev server contained a real side-effect import:

```ts
import "/src/editor/0-core/8-lib/eval/eval.ts";
```

Each worker then executed `new Worker()`, which loaded the worker again. That loop is what filled the renderer heap.

The extra `eval-protocol.ts` file is the stricter fix for this toolchain. Vite 8 still emits `import "./eval-protocol.ts"`, but that module compiles to `export {}` and does not construct a worker, so the loop stops. LosslessCut's `import type` from `./eval` would also stop it here, and it is the smaller match to upstream. It is easier to undo: changing that line back to `import { type }` restores the loop under Vite 8. Keeping the types in a module that does not create the worker stays safe with the import style this codebase uses.

So, which option is better for stable operation: keeping our implementation or using the implementation from LosslessCut?

---

**Cursor**

Keep the current split. It is the more stable choice in this project.

LosslessCut's `import type` from `./eval` is safe only while that statement stays fully type-only. Vite 8 deletes `import type` completely, so the worker never loads the module that calls `new Worker()`. The same line written as `import { type ... }`, which is the form used elsewhere here, is rewritten by Vite 8 into a real import of `eval.ts`. That import is what made each worker start another worker.

`eval-protocol.ts` still gets imported, and the compiled module is empty. It does not create a worker, so the loop cannot start again if the import is rewritten.
